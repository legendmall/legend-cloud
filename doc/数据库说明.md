# 数据库说明

> 本文件说明 legend-cloud 需要初始化哪些库、脚本在哪个位置、表结构的大致划分与命名规律，以及执行脚本前必须注意的风险。
> 内容依据 `master` 分支 `db/` 目录下 SQL 脚本的实际内容整理（读取日期 2026-10-08），表数量与表名均为脚本实测值，非估算。
> 文中未标明的细节（如具体数据源连接池参数、Nacos 中的连接串）**以实际部署配置为准**，本文件不做臆测。

---

## 1. 需要建几个库

项目一共需要 **4 个库**，其中只有 1 个是业务库，另外 3 个是中间件自带的库。

| 库名 | 脚本 | 表数 | 归属组件 | 是否业务数据 |
|---|---|---|---|---|
| `legend_cloud` | `db/legend_cloud.sql` | 202 | 业务库（各微服务共用） | 是 |
| `legend_cloud_nacos` | `db/legend_cloud_nacos.sql` | 12 | Nacos 配置中心 / 注册中心 | 否 |
| `legend_cloud_seata` | `db/legend_cloud_seata.sql` | 5 | Seata Server（分布式事务） | 否 |
| `legend_cloud_xxl_job` | `db/legend_cloud_xxl_job.sql` | 8 | Xxl-Job 调度中心 | 否 |

说明：

- 各中间件脚本均自带 `CREATE DATABASE IF NOT EXISTS` 与 `USE` 语句，库名已固定为上表第一列。如需改名，须同时修改对应组件的连接配置。
- `legend_cloud.sql` 由 SQLyog Ultimate v13.1.1 从 **MySQL 8.0.17** 导出，脚本内包含 `/*!...*/` 形式的 MySQL 条件注释，**不要**拿到其它数据库（PostgreSQL、Oracle、MariaDB 等）上直接执行。

## 2. 初始化顺序与步骤

建议顺序：**Nacos → Seata → Xxl-Job → 业务库**。

原因：所有业务服务的配置与注册都依赖 Nacos（`bootstrap.yml` 中已固定读取 `namespace: legend-cloud`），先把 Nacos 库准备好，服务才能拉到配置；Seata 与 Xxl-Job 各自需要独立库；业务库最后执行。

```bash
# 依次执行（按自己的账号/host 替换）
mysql -h 127.0.0.1 -P 3306 -u root -p < db/legend_cloud_nacos.sql
mysql -h 127.0.0.1 -P 3306 -u root -p < db/legend_cloud_seata.sql
mysql -h 127.0.0.1 -P 3306 -u root -p < db/legend_cloud_xxl_job.sql
mysql -h 127.0.0.1 -P 3306 -u root -p < db/legend_cloud.sql
```

也可以在 MySQL 客户端里用 `source` 导入：

```sql
CREATE DATABASE IF NOT EXISTS legend_cloud DEFAULT CHARACTER SET utf8mb4;
USE legend_cloud;
SOURCE /path/to/db/legend_cloud.sql;
```

执行完建议核对数量：

```sql
SELECT table_schema, COUNT(*) FROM information_schema.tables
WHERE table_schema IN ('legend_cloud','legend_cloud_nacos','legend_cloud_seata','legend_cloud_xxl_job')
GROUP BY table_schema;
-- 期望值依次为 202 / 12 / 5 / 8
```

> 中间件脚本建的表结构与中间件版本强相关。上表为仓库当前脚本的版本，若你部署的 Nacos / Seata / Xxl-Job 版本与仓库声明的不一致，**优先使用中间件官方 release 里自带的 SQL**，不要用旧脚本。

## 3. 业务库表结构总览

`legend_cloud` 共 202 张表，按前缀划分：

| 前缀 | 表数 | 说明 |
|---|---|---|
| `ls_` | 197 | 业务表，统一前缀 |
| `oauth2_` | 3 | Spring Authorization Server 的客户端与授权表（`oauth2_registered_client`、`oauth2_authorization`、`oauth2_authorization_consent`），由 `legendshop-auth` 使用 |
| `leaf_alloc` | 1 | Leaf 号段分配表，由 `legendshop-id` 使用 |
| `undo_log` | 1 | Seata AT 模式回滚日志表 |

关于 `undo_log`：Seata 要求**每一个参与分布式事务的业务库**都要有这张表。仓库已把它放进 `legend_cloud.sql`，业务库执行完即具备条件；`legend_cloud_seata.sql` 里也有一份，那是给独立部署场景备用，不需要在业务库重复执行。

## 4. 命名与字段规范（脚本实测归纳）

以下规律是从现有 202 张表统计出来的，新增表时建议沿用：

| 项 | 现状 |
|---|---|
| 表名 | 小写 + 下划线，统一 `ls_` 前缀；中间件的表保持组件原名（`oauth2_*`、`xxl_job_*`、`leaf_alloc`、`undo_log`） |
| 主键 | 188 张表单列主键 `id`；其余为联合主键或无主键 |
| 主键类型 | 绝大多数为 `int(11)` / `int(11) unsigned`，少量 `bigint` |
| 时间字段 | 常用 `create_time` / `update_time`，类型 `datetime`，部分带 `COMMENT` |
| 软删除 | 少量表使用 `del_flag`（12 处），并非全库统一 |
| 状态字段 | `status`（75 处） |
| 归属字段 | `shop_id`（53 张表）、`user_id`（71 处）、少数表有 `company_id` |
| 金额 | `decimal(15,2)` |
| 注释 | 168 张表有表级 `COMMENT`，其余 34 张缺失 |
| 引擎 | 全部 InnoDB |
| 字符集 | `utf8mb4`，但排序规则混用 `utf8mb4_general_ci` 与 `utf8mb4_0900_ai_ci` |
| 逻辑删除对象 | 脚本中无视图、存储过程、触发器、函数 |

新增表时建议：表名带 `ls_` 前缀 → 主键 `id` → 统一 `create_time` / `update_time` → 必须有表级 `COMMENT` → 字段全部加 `COMMENT`。

## 5. 数据库连接配置在哪里

仓库里**没有**数据库连接串。各服务的 `src/main/resources/bootstrap.yml` 只配置了 Nacos 的地址，形如：

```yaml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: ${NACOS_HOST:http://localhost}:${NACOS_PORT:8848}
        namespace: ${NACOS_NAMESPACE:legend-cloud}
      config:
        file-extension: yml
        shared-configs:
          - data-id: application-${spring.profiles.active}.${spring.cloud.nacos.config.file-extension}
            refresh: true
  config:
    import:
      - optional:nacos:${spring.application.name}.${spring.cloud.nacos.config.file-extension}
```

也就是说：

1. 数据源地址、库名、账号密码都放在 **Nacos 配置中心**，命名空间默认 `legend-cloud`；
2. 需要改库名或账号，改的是 Nacos 上的 `application-{profile}.yml` 与各服务同名配置，**不是改仓库代码**；
3. 本地起服务却连不上库，第一步应检查 Nacos 上对应的 data-id 是否已导入。

> 上述键名与默认值取自 `business/legendshop-product/legendshop-product-service/src/main/resources/bootstrap.yml`，其它服务结构相同，具体值以各服务实际文件为准。

## 6. 执行脚本前必须知道的 8 件事

按重要程度排序，前两条会直接导致数据丢失。

1. **脚本会先删表**：`legend_cloud.sql` 中每张 `CREATE TABLE` 前都跟着 `DROP TABLE IF EXISTS`（共 202 处）。**只能在全新的空库上执行**，对已有数据的库执行会清空全部表。脚本本身没有做「已存在则跳过」的判断。
2. **只有表结构，没有初始化数据**：整个 `legend_cloud.sql` 中没有任何 `INSERT` 语句。执行完得到的是一个空库，平台管理员账号、字典、地区数据、菜单权限等基础数据需要另行准备（通过后台初始化或找维护方索取）。
3. **必须用 MySQL 8.0**：部分表使用 `utf8mb4_0900_ai_ci` 排序规则，这是 MySQL 8.0 才引入的，5.7 上执行会报 `Unknown collation`。
4. **主键是 int，容量有上限**：绝大多数表主键为 `int(11)` / `int(11) unsigned`，上限约 21 亿 / 42 亿。订单、流水、日志类高频表如果长期大批量运行，需要提前评估是否改 `bigint` 或做归档。
5. **3 张表没有主键**：`ls_admin_user_role`、`ls_pay_settlement_log`、`undo_log`。`undo_log` 无主键是 Seata 官方脚本风格，另外两张建议补上联合主键，便于主从复制与后续维护。
6. **34 张表缺表注释**，索引命名也不统一（同时存在 `UNI_ADMIN_USER_NAME`、`user_id_unique`、`role_id`、`time` 等风格）。做二次开发时不要照搬旧风格，新增索引建议统一用 `idx_xxx` / `uk_xxx`。
7. **`leaf_alloc` 有两处**：业务库脚本里有一份，`business/legendshop-id/legendshop-id-service/scripts/leaf_alloc.sql` 里也有一份，后者末尾带一条「从 `ls_sequence` 迁移号段」的 `INSERT ... SELECT`。而 `ls_sequence` 表在脚本里**没有任何初始数据**，这条迁移语句查不到数据。使用 `legendshop-id` 时，需要自己给 `leaf_alloc` 插入 `biz_tag`（每张需要发号的表一个），步长按业务量设置。
8. **连接参数在 Nacos，不在仓库**：见上一节。改库名/密码请改 Nacos 配置。

其它 SQL 文件：

- `business/legendshop-id/legendshop-id-service/scripts/leaf_alloc.sql` —— ID 服务的号段表。
- `common/legendshop-common-monitor/src/main/resources/support/monitor/mysql/*.sql` —— 监控模块自带脚本，不属于初始化必需项，用途以该模块说明为准。

## 7. 已发现的遗留问题

整理本文时实测发现，记录在此避免重复踩坑：

1. `legend_cloud.sql` 全量 `DROP TABLE IF EXISTS`，且没有配套的基础数据脚本，新环境初始化后系统无法直接登录使用（缺管理员、菜单等数据）。
2. 排序规则混用 `utf8mb4_general_ci` 与 `utf8mb4_0900_ai_ci`，跨版本迁移时会遇到排序规则冲突。
3. `ls_sequence`（旧 ID 序列表）与 `leaf_alloc`（新号段表）并存，且 `ls_sequence` 无初始数据，迁移路径是断的。
4. 34 张表缺表注释、3 张表缺主键、索引命名不统一。
5. 业务库中**没有 `tenant_id` 字段**；出现频次最高的归属类字段是 `shop_id`（53 张表）。租户隔离维度的具体实现以代码为准，另见后续的多租户说明文档。
