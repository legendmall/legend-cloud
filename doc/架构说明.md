一级目录职责：

## 3. 业务服务清单（business/）

| 服务目录 | 职责 |
|---|---|
| `legendshop-gateway` | 网关，统一入口。含 `Dockerfile`、`docker-entrypoint.sh` |

### 3.1 `*-api` 与 `*-service` 分包约定

已确认 `legendshop-basic`、`legendshop-order` 内部均拆为两个子模块：

```
business/legendshop-basic
├── legendshop-basic-api       # 对外暴露的 Feign 接口 + DTO
└── legendshop-basic-service   # 业务实现 + Controller，可独立部署
```

**约定**：服务 A 要调用服务 B，只需在 A 的 `pom.xml` 中引入 B 的 `*-api` 模块，**不要引入 `*-service`**。这样可以避免模块循环依赖，也避免把对方的实现类带进自己的 classpath。

> 其余服务是否同样拆分为 api / service 两个子模块，请以实际目录为准；新建服务时建议沿用该约定。

## 5. 一次请求的调用链

以「用户端下单」为例（示意，具体类名以实际代码为准）：

1. 前端请求打到 `legendshop-gateway`，网关完成路由匹配与鉴权（令牌校验）；
2. 网关通过 Nacos 拿到目标服务的实例列表，经负载均衡转发；
3. `legendshop-order` 处理下单逻辑，需要校验商品与库存时，通过 OpenFeign 调用 `legendshop-product-api` 暴露的接口；
4. 跨服务写操作若涉及分布式事务，由 Seata 协调；
5. 需要异步解耦的部分（如订单状态通知、库存回滚）投递到 RabbitMQ；
6. 服务间调用与降级受 Sentinel 保护；
7. 多租户场景下租户标识随调用链透传，由数据层完成隔离（机制另见多租户说明文档）。

## 9. 已发现的口径冲突与遗留问题

整理文档时实测发现，记录在此避免重复踩坑（**不影响按本文档搭建**）：

1. **Seata 版本冲突**：主 `README.md` 写 `1.7.0`，根 `pom.xml` 的 `seata.version` 为 `1.4.0`。选型时以实际引入的依赖为准。
2. **`doc/README.md` 版本表与主 README 不一致**：Redis 版本号疑似误填为 Maven 版本、RabbitMQ 版本缺失、多处下载链接指向 Maven 官网。
3. **`doc/环境搭建/docker-compse一键安装/docker-compose.yaml` 为 0 字节空文件**，一键启动不可用；`doc/环境搭建/README.md` 仍描述 rocketmq（当前用 RabbitMQ）、MinIO 桶名与引用的 `es/order.md` 均已失效。详见 `doc/部署指南-DockerCompose.md`。
4. ⚠️ **根 `pom.xml` 的 `<properties>` 中含明文的私有 Docker 仓库账号密码与内网主机地址**。公开仓库不应携带凭据，建议移至 Maven `settings.xml` 或构建环境变量，并轮换已暴露的密码。
